|---|---|---|---|---|
| **이름** | ✅ | Google(Firebase) | 앱 기능(계정 관리) | 필수 |
| **이메일 주소** | ✅ | Google(Firebase) | 앱 기능(계정 관리) | 필수 |
| **사용자 ID** | ✅ | Google(Firebase) | 앱 기능(계정 관리) · 사기 방지(식별 한도) | 필수 |

**신고하지 않아야 하는 것** — 방침에는 적혀 있으나 코드에 없다:

**삭제 요청 경로**: 있음 — 앱 내 설정 → 계정 삭제 (`DELETE /api/v0/users/me`)

> ⚠️ 현재 신고는 **「수집 없음 · 공유 없음」** 이다. 위 5개 유형 전부 미신고 상태다.

## 2. 근거 — 기기에서 나가는 것 전부

### 2-1. 엔드포인트 전수 (`core/network/.../api/`)

```
POST   /api/v0/auth/kakao/token      카카오 액세스 토큰 → Firebase Custom Token 교환
GET    /api/v0/consents              필수 동의 항목 조회 (인증 불필요)
GET    /api/v0/users/me              회원 정보·동의 상태
POST   /api/v0/users/me/consents     동의 기록 저장
DELETE /api/v0/users/me              회원 탈퇴
GET    /api/v0/pill-attributes/usage 남은 식별 횟수
POST   /api/v0/pill-attributes       ⚠️ 낱알 크롭 이미지 전송
POST   /api/v0/pill-candidates       속성으로 후보 조회 (이미지 없음)
GET    /api/v0/pill-details/{code}   품목 상세 (이미지 없음)
POST   /api/v0/pill-images/upload-url ⚠️ 원본 사진 업로드 URL 발급
```

### 2-2. 모든 인증 요청에 붙는 헤더

- `Authorization: Bearer <Firebase ID 토큰>` — `AuthHeaderInterceptor:38`
- `X-Firebase-AppCheck: <App Check 토큰>` — `AppCheckInterceptor:36` (릴리스는 Play Integrity)

> `X-Device-Id`는 **폐기됐다.** `DeviceIdRepository`가 남아 있지만 **어디서도 쓰이지 않는 dead code**다
> (호출처 0건 확인). 기기 식별자는 전송되지 않는다.

### 2-3. 사진 — 두 경로로 나간다

**① 낱알 크롭 (필수 경로)**
`PillAttributeItem(pillId, croppedImage)` → `POST /pill-attributes`
- 온디바이스 검출 후 마스크를 알파에 넣은 **투명 배경 PNG**, base64
- 서버가 **Gemini(Google)** 로 색·모양·제형을 분류 → **제3자 공유에 해당**

**② 원본 사진 (베스트 에포트)**
`PillRecognitionViewModel.kt:182-191` → `POST /pill-images/upload-url` → presigned URL 로 PUT
- **JPEG일 때만** 보낸다(`contentResolver.getType(uri) != JPEG_MIME` 이면 중단). 촬영 결과는 항상 JPEG,
  갤러리에서 고른 HEIC·PNG는 제외된다.
- 결과를 기다리지도 확인하지도 않는다(식별 플로우와 분리).
- ⚠️ **사용자에게 "원본 사진도 서버에 올라간다"는 안내가 없다.** 데이터 보안 신고에는 반드시 포함해야 한다.

> ⚠️ **약포 사진에는 환자 정보가 찍힐 수 있다**(약국 봉투에 이름·처방 정보). 실제 테스트 사진에는
> 없지만, 실사용자 사진에는 들어갈 수 있다 — 취급 방침은 §6 참조(미정).

### 2-4. 이름·이메일 — 우리 서버가 아니라 Firebase에 들어간다

우리 서버의 회원 모델(`core/model/User.kt`)에는 **이메일 필드가 없다**:
```
userId · provider · providerUserId · createdAt · consents[]
```

그런데 **Firebase Auth 레코드에는 이름·이메일이 들어간다**:
- **애플**: `FirebaseAuthRepository.kt:78` — `setScopes(listOf("email", "name"))` 으로 **명시적으로 요청한다.**
  KDoc에 "지금 화면에서 쓰진 않지만 Firebase가 프로필에 채워 두도록 요청해 둔다"고 적혀 있다.
- **구글**: `GetSignInWithGoogleOption` — ID 토큰에 이메일이 포함된다.
- **카카오**: 코드에서 scope를 지정하지 않는다 → 개발자 콘솔 동의항목 설정을 따르는데,
  **이메일로 설정돼 있다(확인됨).** 서버가 토큰을 검증해 Firebase Custom Token을 만든다.

**앱 코드는 이메일을 읽는 곳이 없다**(`grep` 결과 위 두 줄이 전부). 즉 우리가 쓰진 않지만 **수집은 된다** —
Play 기준으로는 수집·공유 신고 대상이다.

### 2-5. 기기에 남기는 것

우리 앱이 직접 영속하는 사용자 데이터는 **없다.** DataStore를 쓰는 곳은 dead code인
`DeviceIdRepository` 뿐이다. Firebase Auth SDK가 자체 토큰 캐시를 남기는 것은 SDK 내부 동작이다.

디버그 빌드에만 `PillAttributeCache`(직전 속성 결과 캐시)가 있고 **릴리스에서는 늘 null**이다.

### 2-6. 분석·크래시 리포팅 — 없다

`gradle/libs.versions.toml` 확인 결과 Firebase 의존성은 **auth · appcheck · appcheck-playintegrity**뿐이다.
**analytics·crashlytics·performance 없음.** 따라서 사용 기록·진단 정보 수집은 신고 대상이 아니다.

### 2-7. 권한

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.CAMERA" />
```
갤러리는 `PickVisualMedia`(포토 피커)를 써서 **저장소 권한을 요구하지 않는다** — 사용자가 고른 사진만 받는다.

## 3. 제3자 정리

| 대상 | 무엇이 가나 | 성격 |
|---|---|---|
| **Google — Firebase Auth** | 이름·이메일·소셜 공급자 ID | 인증 처리(처리자). Play 기준 "공유"로 신고 |
| **Google — Play Integrity** | 앱·기기 무결성 증명 | App Check. 사용자 데이터 아님 |
| **Google — Gemini** | 낱알 크롭 이미지 | **서버 경유**. 사진 "공유"에 해당 |
| **카카오** | 카카오 액세스 토큰 | 로그인 공급자. 동의항목 = **이메일**(확인됨) |
| **자사 서버 (dev/prod)** | 위 전부 + 동의 기록 | 자체 인프라 |

> 스토어 신고서에는 Gemini 경유를 "제3자 공유"로 볼지 "처리자 위탁"으로 볼지 판단이 필요하다.
> Play 데이터 보안 기준으로는 **서비스 제공을 위한 전송도 "공유"에 포함**되므로 신고하는 쪽이 안전하다.

## 5. ⚠️ 개인정보처리방침과 코드가 어긋난다 — 3건

방침 원문: <https://www.nursemate.app/privacy/> (시행일 2026-09-01, 서버 `version` 과 일치 ✓)

### 5-1. 「카카오는 이메일 미제공」 — 틀렸다

- **방침**: 이메일은 "구글·애플 로그인 시 제공되나 조회·이용하지 않음", **카카오는 미제공**
- **실제**: 카카오 개발자 콘솔 동의항목이 **이메일**로 설정돼 있다(확인됨)
- → 방침을 "구글·애플·카카오 모두 제공받으나 조회·이용하지 않음"으로 고쳐야 한다

### 5-2. 「이름은 수집하지 않음」 — 틀렸다

- **방침**: 수집 항목에 이름이 **없다**
- **실제**: `FirebaseAuthRepository.kt:78` 에서 애플 로그인에 **`setScopes(listOf("email", "name"))`**
  으로 이름을 **명시적으로 요청**한다. Firebase 프로필에 채워진다.
- → 방침에 이름을 추가하거나, **요청 scope 에서 `name` 을 빼야** 한다.
  앱이 이름을 쓰는 코드는 없으므로 **scope 를 빼는 쪽이 깔끔하다**(수집 최소화).

### 5-3. 「앱 이용 통계·오류·진단 데이터 수집」 — 실제보다 과하게 적혀 있다

- **방침**: 수집 항목에 "앱 이용 통계, 오류·진단 데이터" 포함
- **실제**: Firebase 의존성이 **auth · appcheck · appcheck-playintegrity** 뿐. analytics·crashlytics **없음**
- → 수집하지 않는 것을 수집한다고 적은 상태다. 방침에서 빼거나, 실제로 붙일 계획이면 그때 넣는다.
  **Play 데이터 보안에는 넣지 않는다**(넣으면 또 다른 불일치가 된다).

### 5-4. 방침과 코드가 **일치하는** 것 (조치 불필요)

- 알약 사진 수집·목적: "식별" + **"알약 인식 모델의 학습·개선"** ← 원본 사진 업로드(§2-3 ②)의 근거가 여기 있다
- 보관: "목적 달성 후 지체 없이 파기", 익명·비연결 유지
- 탈퇴: 회원 정보·동의 기록·Firebase 계정 삭제, **이용 한도 식별값·일일 기록은 파기 제외**
  (spec `api/domains/auth.md` §탈퇴의 `daily_usage` 예외와 일치 ✓)
- 제3자: Google LLC(Gemini 분류·Firebase) · 카카오 · Apple · AWS(서버·이미지 저장) 모두 명시 ✓

> 원본 사진의 실제 파기가 방침대로 이뤄지는지는 **서버 쪽 확인이 필요하다**(영빈 님).
> 방침에 "지체 없이 파기"라고 썼으므로 S3 라이프사이클이나 배치 삭제가 실제로 도는지 봐야 한다.

## 6. 결정이 필요한 것 — 약포 사진의 민감정보

약국 봉투에는 **환자 이름·처방 정보가 인쇄돼 있을 수 있다.** 사용자가 그대로 촬영하면 그 이미지가
서버로 가고(§2-3), 방침에 따르면 **모델 학습에도 쓰인다.**

현재 방침은 알약 사진을 "익명·비연결"로 다룬다고만 적고, **봉투에 찍힌 제3자(환자) 정보**는 다루지 않는다.

선택지:
1. **촬영 화면에서 안내** — "환자 정보가 보이지 않게 촬영해 주세요" 한 줄. 가장 싸고 즉시 가능.
2. **크롭만 전송** — 원본 업로드를 끊고 낱알 크롭만 보낸다. 학습 데이터를 잃지만 위험이 사라진다.
3. **방침에 명시** — 봉투에 정보가 포함될 수 있고 학습 전 비식별 처리한다고 적는다. 실제 처리가 뒷받침돼야 한다.

권고: **1 + 3 병행.** 2는 학습 데이터를 잃어 아깝고, 안내만으로는 완전하지 않으니 방침에 사실대로
적는 편이 안전하다. 다만 이건 법무·정책 판단이 섞이므로 **팀 결정 사항**이다.
